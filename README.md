# C盘守护者

Windows 桌面文件分析工具：扫描大文件，解释常见软件文件的用途，并给出保守的清理建议。它也用于研究本地小模型的量化、微调和检索增强生成。

## 当前功能

- **文件扫描**：仅使用 MFT 双读取 worker：2 个线程、独立卷句柄、4 MiB 块、4 个缓冲区，固定交替读取。需要管理员权限、NTFS 和整盘根目录；候选文件按句柄核验逻辑大小。结果页面直接显示文件，诊断在折叠详情与报告中保留。未经逐文件核验的小文件和运行中原始记录仍有一致性限制，不包含命名数据流或时点快照。
- **结果完整性**：后端保留全部命中结果，按批核对序号、数量以及路径和大小的 SHA-256 摘要，传输不完整时从后端分页恢复；恢复页也验证内容和偏移。摘要只计算结果元数据，不读取文件内容。前端每页显示 100 条，分类、全选和复制仍涵盖当前分类的全部页；导出不再截断为 1000 条。硬链接按路径显示，合计可能重复计算同一文件实体。
- **结构化文件释义（本分支）**：先展示文件属性、附近模型配置和环境标记，再由模型输出归属用途、删除影响、恢复条件、处理建议四项说明，同时列出依据和未知项。本地 llama.cpp 使用 GBNF 约束 JSON；格式合格不代表结论准确。使用方式与边界见[开发记录](docs/file-explanation/IMPLEMENTATION.md)。
- **可选联网与云端**：用户确认展示的通用查询词后，使用 Tavily 查询限定官方域名的资料，保留原文片段和链接；查询不含实际路径、文件名或问题。搜索失败会明确提示。本地生成不发送证据到云端模型；选择 OpenRouter/OpenAI 兼容接口时，会发送完整路径、本机线索和问题，界面会提前说明。
- **安全分类**：红色为系统关键位置，黄色表示需要确认，绿色表示已识别的可清理类别。缓存名称、下载目录或 `.bak` 扩展名本身不足以判定安全；绿色也需要确认是否在用、是否需保留。
- **用户操作**：可打开文件所在位置，也可在界面中选择文件并确认移入回收站。项目实际存在删除功能，早期“不会执行任何删除操作”的说明不准确；AI 解释不会自动触发删除。

路径只能提供线索，不能证明文件内容、应用依赖或备份状态。未知路径应明确说明无法确定，解释和颜色都不能作为数据可恢复的保证。

## 实验和验证

### 第二轮：表达多样性与困难负例（2026-10-10）

已在训练前[公开计划](https://github.com/szaaaaaa/C_manager/blob/86385a7935bb47b9b8781a97cef288ba495cc884/lora-training/experiments/2026-10-10-round2/plan.md)，完成三组新鲜 Qwen3.5-4B NF4 LoRA 训练和四组同输入评估。A使用单一表达，B保持输入与事实相同，改变目标答案措辞与长度，C在B基础上等量替换困难负例；各160条训练、共享32条验证，各40步并仅按验证NLL选择检查点。288条回答先匿名逐条评分，19条一致性修订保留完整前后记录，评分与修订日志冻结后才揭盲。主评是新48条，历史24条单列。

| 主评条件 | 严格资料忠实性 | 未知拒猜 | 已知解释完成 | 危险主张 |
|---|---:|---:|---:|---:|
| 旧适配器 | 31/48 | 14/20 | 23/28 | 2 |

**四组都未达到全部事先质量目标。** A→B没有改善忠实性，B→C有部分改善，仍不能称C比旧适配器全面可靠。C对监督留出的npm/Git两家族8条回答全部资料支持，但只有6/8同时支持且完整，低于7/8目标；各组自然度均值仍低于4。C的验证NLL最低也不代表解释质量最佳。见[完整报告](lora-training/experiments/2026-10-10-round2/report.md)、[分析和逐项证据](lora-training/experiments/2026-10-10-round2/analysis.md)、[可复算汇总](lora-training/experiments/2026-10-10-round2/review-summary.json)及[进度](lora-training/experiments/2026-10-10-round2/progress.md)。

评审为同助手条件匿名审阅，不能替代真人评价；路径为合成案例、单seed，评估只提供冻结用途资料，没有测试实际扫描检索链。旧适配器的历史24条回答与第一轮逐字相同，本轮重评13/24与第一轮17/24的差异来自评分判读和一致性校准，不是模型行为变化。权重和缓存保存在D盘，GitHub保存研究证据与权重SHA清单；新适配器尚未导出GGUF或接入应用，加载峰超过7GB余量目标。

## 开发

需要 Windows、Rust stable、Node.js，以及 [Tauri 2 开发环境](https://tauri.app/start/prerequisites/)。本地模型文件不存入 Git，需按微调说明生成或放置模型。

```powershell
cd frontend
npm install
npx tauri dev
```

设置中选择本地模型并加载，或配置云端 API Key、Base URL 和模型名。开发版优先读取 `lora-training/output/finetuned_model_gguf/qwen3.5-0.8b-q4_k_m.gguf`，然后尝试 `src-tauri/resources/`。修改或替换模型后需重启应用重新加载。

```powershell
# 前端检查
cd frontend
npm test
npm run lint
npm run build

# Rust 单元测试（从项目根目录执行）
cd ../src-tauri
cargo test --lib
```

实际模型测试默认忽略，可用 `local_model_chinese_and_explanation_smoke` 配合 `--ignored --nocapture` 运行。Windows 完整扫描基准默认创建并清理独立临时夹具，包含 18,563 个文件、阈值边界和 20 GiB 稀疏文件，与生成时的独立清单核对。预热后按 0 / 100 MiB 两种阈值交错比较 1/2/4/8 个工作线程，各运行 3 次并逐条比较路径与大小。阶段耗时为各工作线程耗时之和，`elapsed_ms` 为实际总耗时：

```powershell
# 从 src-tauri 执行；不设置 SCAN_BENCH_ROOT 时自动生成夹具
cargo test --release --lib complete_scan_performance -- --ignored --nocapture
# 可选：设置 SCAN_BENCH_ROOT 对稳定的现有目录做只读基准；此时以预热结果对照，没有独立清单
```

2026-10-10 本机 Windows debug 构建、热缓存夹具：128 个子目录各 128 个文件，根目录另有 2048 个文件，每个文件 128 字节。全部配置均找到 18,432 个文件，路径和大小逐条一致、零错误。1/2/4/8 线程的三次中位耗时分别为 961/633/424/313 毫秒；默认采用 4 线程。此结果仅衡量该夹具的后端完整扫描，不代表冷缓存、机械硬盘、整盘或界面总耗时。

`cargo run --bin export_scan -- <root> <min_size_mb> [mft_dual]` 导出全部匹配文件；默认只使用双读取 worker，旧引擎参数明确拒绝。报告保留真实完整性状态，部分完成或取消退出码为 2。

当前产品仅保留原版双读取 worker；目录遍历仅作为测试中的正确性参考，不编入应用。上面的历史目录基准不代表当前引擎性能。本轮按用户要求只编译构建、不执行测试，选择依据是用户多次实测原版约 4.x 秒，其他实验方式约 5 秒。详见 [收敛记录](docs/scan-validation/2026-10-10/SINGLE_ENGINE.md)。

## 构建

先将经过验证的 `qwen3.5-0.8b-q4_k_m.gguf` 放入 `src-tauri/resources/`，再执行：

```powershell
cd frontend
npx tauri build
```

安装包位于 `src-tauri/target/release/bundle/`。模型作为 Tauri resource 打包；模型加载、BF16 实验和安装包端到端验收是不同的检查，实验报告会说明实际完成了哪些。

仅构建独立运行的测试程序时，先完成前端生产构建，再在 `src-tauri` 执行 `cargo build --release --bin c-manager --features tauri/custom-protocol`。普通 `cargo build --release` 未启用内嵌资源协议，不能作为独立窗口运行的验收依据。
