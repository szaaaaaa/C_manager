# 极小模型文件解释实验：结果与结论

执行日期：2026-10-09 UTC / 2026-10-10 北京时间。模型为 Qwen3.5-0.8B，GPU 为 RTX 5070 Laptop（约 8GB）。[协议](PROTOCOL.md)、[测试集](../../data/eval_cases.json)、[逐条审阅](review.json)、[统计数据](summary.json) 和原始回答一起保存。以下是受控小样本的结果，不是全软件覆盖的准确率。

## 结果

| 配方 | 固定关键词检查 | GPU 生成耗时中位数 | 范围 |
|---|---:|---:|---:|
| 原始基础模型，无资料 | 8/24 | 3.02 秒 | 2.08–9.58 秒 |
| 本次纯 SFT 配方，无资料 | 5/24 | 3.11 秒 | 1.86–10.41 秒 |

原始结果：[base-plain.json](base-plain.json)、[sft-plain.json](sft-plain.json)、[base-rag.json](base-rag.json)、[sft-rag.json](sft-rag.json)。四组显式启用推理缓存、greedy 解码、相同系统指令和安全分类；资料只附加在 RAG 组。耗时不含加载，首条可能含预热，输出长度也不相同。因此不能把中位数差异视为算法吞吐量优势，更不能当成桌面 CPU 的响应时间。

关键词检查存在假阳性和假阴性。新模型的 pip `.body` 回答通过检查，但说成“下次运行 python 包时仍需重新下载”；正确含义是以后安装/下载时可能重下，已安装的包不因此失效。两个 WebView 回答因没有“依赖”二字失败，但已经指出其他应用需要运行库；一条临时文件回答没有重复“临时”二字，也失败。这些例子说明 **21/24 不等于 87.5% 事实准确率**。

## 逐条审阅发现

纯 SFT 有明显的错误泛化：把用户名 `Eval` 当成软件名，给 `archive.bin` 编造调试数据用途，把 Node.js 依赖叫作 Python 项目，把 WebView2 Runtime 混同 Edge 浏览器，并对 OneNote 缓存遗漏未同步笔记损失。已修正的数据格式和训练接口并没有自动解决事实可靠性。历史训练参数和数据哈希见 [pure-training.json](pure-training.json)；旧输入快照及权重只保留在本机，当前纯 SFT 数据又做过纠错，不能用它严格复现这组历史权重。

基础模型加资料后，WebView2 和 PyTorch 的用途更接近资料，也更少编造具体软件，但多条回答遗漏了删除后果、重新安装或离线影响。`cache-backup` 仍被猜成 Python 缓存备份。

检索感知 SFT 在本轮明显改善了资料使用和未知用途校准：六个未知/近似路径都明确承认无法确定；正确资料缺失时也没有编造 OneNote 文件细节；混入 pip 资料时没有把 WebView2 解释成 Python 缓存。PyTorch、依赖目录和模型缓存的处理建议更完整。

问题仍然存在：pip 的安装/运行混淆，OneNote 回答把“未同步且没有其他副本的修改可能无法从云端恢复”压缩成过于绝对的“云端也无法恢复”，以及“保留需要修改的修改内容”等僵硬文字。未知路径的七条回答完全相同，说明谨慎表达学会了，但语言多样性没有解决；增加训练 epoch 不能保证改善这一点。

`review.json` 是 Codex 按提供资料作的一次逐条审阅，记录了依据和遗漏，未做盲评或专家复核。它不验证测试路径上真实文件的内容，也不作为独立人评准确率。

## 训练和导出

检索感知数据共 168 条，其中相关资料 96、混合资料 16、无关资料 16、缺失资料/未知路径 40。150 条训练、18 条验证；**pip-cache 整类留作验证**，未把它的路径改写混入训练。

BF16 LoRA：r=16、alpha=16、dropout=0.05，batch=2、梯度累积=4、lr=1e-4，2 epoch，共 38 step，训练用时 398.24 秒；可训练参数 6,389,760 / 859,375,680。每 10 step 验证，采用 checkpoint-20（验证 loss 1.6574），最终重新验证为 1.6582。训练指标见 [rag-training.json](rag-training.json)。该 loss 与纯 SFT 的另一份验证数据不能直接比较。

本机 Unsloth 提示该模型未接收 `num_items_in_batch`，梯度累积存在归一化精度限制；本轮未更改库实现，也未做 batch/累积的单独对照。数据类别只有八种，重复路径变体不是独立知识样本；验证集也很小。

早期纯 SFT 的 HF 导出保留了 `use_cache=false`，导致耗时比较失真。已统一为 `use_cache=true` 并重跑表中三组基线，保存模型时也恢复推理缓存。Tokenizer 文件在基础和纯微调模型中完全相同，没有按 Mistral 警告擅自修改 Qwen 分词规则。

量化采用同一套 llama.cpp 转换器和 quantizer，先保存合并 BF16 权重，再转 Q4_K_M，成功后原子替换最终文件。当前 Unsloth 的单文件下载/探测 GGUF 路径曾因 upstream 新增 `conversion` 包而失败，改为调用配套完整工具链。没有用遗留 GGUF 伪装新导出。

原生 CPU llama.cpp 的中文/emoji 字节解码及六条解释 smoke 测试通过，测试进程计时 16.84 秒（含模型加载和多条推理）。原始回答和模型 SHA256 见 [native-smoke.json](native-smoke.json)。本机开发和资源目录已换为该实验模型并核对哈希，旧资源保留在忽略的输出目录。这是量化后的有限场景验证，不能证明 BF16 和 Q4 的所有回答等价，也没有安装包或桌面 GUI 端到端验收。

## 工程修复

- 扫描回退遵守用户深度，目录扫描不误枚举整卷，USN 路径缓存只保存目录；取消与 USN 异常读取不会被当作完整扫描成功，完成进度不受 top-N 截断影响。子目录权限等无法读取的项仍会跳过。
- 本机浅层回退扫描由强制 30 层的 100.94 秒变为配置 3 层的 3.56 秒，覆盖范围不同。这是参数修复的效果，不是完整扫盘的吞吐量比较；管理员 USN 全盘性能没有实测。
- 本地生成按字节拼接后解码，修正拆分 UTF-8 字符被丢弃的问题；训练和推理使用一致的非思考模板。
- 不再将任意 cache、下载目录、备份/日志扩展名标成放心删；OneNote 缓存为需要确认，绿色标签改为可清理。系统关键规则优先于软件资料。
- 文件解释和追问都接入相同本地资料。检索只是路径条件匹配，资料库目前覆盖八类，不读取文件内容，也不能证明备份或依赖状态。
- 修正快速切换文件时旧解释覆盖新文件、旧错误清除新请求加载状态、关闭后旧结果仍回填的问题。三个乱序请求回归测试在修复前均失败，修复后均通过；旧后台推理仍会完成，但结果不会覆盖当前界面。
- 前端三个回归测试、build、lint（零错误，两个既有 hook 警告）与 Rust 检查通过；真实模型 smoke 测试通过。未执行真实用户文件删除。

## 结论

本轮支持把微调目标从“背诵所有文件知识”改成“依据资料说明用途、影响和不确定性”。本地路径检索＋检索感知 SFT 是值得继续的方向，已经改善了这批关键案例；它仍不能消除幻觉、自动证明可删或解决全部文字僵化。

这四组的数据、训练预算和监督方式不同，因此不能把差异全部归因于 RAG 或 LoRA，也不能据此认定 0.8B 没有闭卷学习能力。纯 SFT 失败同时反映了旧数据质量、覆盖不足和训练配方问题。后续应先做同一事实/答案、同一预算的闭卷/开卷训练对照，再引入独立软件类别的新盲测；不要在这 24 条上反复调参后继续把它们叫作独立测试。

若继续改善语言和谨慎程度，可收集同事实的自然改写，并以已核对的正确回答和模型错误回答构造偏好对，再测试 [DPO](https://arxiv.org/abs/2305.18290)。本轮未运行 DPO、GRPO、更大模型或全参数微调，不能宣称它们有效。向量检索也应在资料规模和检索召回需要时再加入，而不是用更复杂的检索替代事实审查。
